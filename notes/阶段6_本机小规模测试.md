# 阶段6：本机小规模测试与结果解读

2026-10-21 已在本机实际运行。本阶段目标是验证小模型的数据、训练、评估、保存和生成链路，理解每个结果能说明什么。

## 1. 本次使用的电脑与模型

| 项目 | 实际配置 |
| --- | --- |
| 显卡 | NVIDIA GeForce RTX 5060 Laptop GPU，约 8GB 显存 |
| Python / PyTorch | 3.13.12 / 2.10.0+cu128 |
| 主实验精度 | FP32，参数和主要计算采用单精度浮点数 |
| 模型参数量 | 100,352，约 10 万参数 |
| 模型结构 | 2 层 decoder，隐藏维度 64，4 个查询头，2 个 KV 头，SwiGLU 中间维度 176 |
| 分词 | 仅用训练文档构建的字符级词表，123 个 token |
| 数据 | 项目自带的 3 篇教学短文，2 篇训练、1 篇验证 |
| 序列长度与 batch | 每条 32 个 token，每小批最多 2 条，梯度累积 2 次 |
| 训练 | AdamW，固定学习率 0.003，100 次参数更新，随机种子 0 |

字符级分词器通常把一个字符当成一个 token；英文单词也可能被拆成多个字符。它用于理解数据流，与官方 Qwen 分词器的切分方法和词表不同。

## 2. 先理解验证项目

**模块测试：11 项通过。** 覆盖张量形状、前向和反向传播、因果遮罩、数据去重切分、分词器序列化、KV cache 等，并增加了训练日志的回归测试。

**单批过拟合：通过。** 将同一小批 token 反复训练 100 次，loss 从 4.1791 降到 0.0105。这检查模型能否通过反向传播和优化器更新学会一个简单样本。这里让模型记住样本正是测试目的，不能据此判断它能回答陌生问题。

**保存恢复：通过。** 保存模型后重新创建模型、加载参数，同样输入的 logits 最大绝对差为 0.0。logits 是模型给词表中每个候选 token 的原始分数。这说明本次参数保存恢复没有改变预测结果；尚未证明中断重启后的数据顺序和整个训练过程逐位一致。

**KV cache：通过。** 全序列计算与缓存历史 K/V 后逐 token 计算的 logits 最大差约为 2.38×10^-7，在本次容差之内。这个测试检查缓存是否改变预测，不代表已经做过长文本性能评测。本次独立 KV cache 入口默认在 CPU 运行。

**BF16：本机前向检查通过。** 本机支持 BF16，loss 有限。主训练实验使用 FP32。服务器的 V100 不支持原生 BF16，迁移时仍需单独适配 FP32 或 FP16 混合精度。

## 3. 图的坐标先看懂

曲线位于 `../artifacts/local_smoke_20261021/loss_curve.png`。

**横轴是 optimizer step，即参数更新次数。** 一次更新前读取两批数据、累积梯度，再由 AdamW 修改参数。因此它不等于文档数，也不等于 GPU 计算量 FLOPs。step=0 是训练前的初始模型。

**纵轴是 next-token cross-entropy loss，即下一个 token 预测的交叉熵损失。** 模型先根据前面的字符，为下一个字符给出概率，再取真实字符概率的负自然对数。真实字符的概率越高，loss 越低。图中每个点都对对应集合重新评估，按有效预测位置数加权平均。

长度为 32 的一条序列，有 31 个预测目标。例如输入“今天学习模型”，模型依次学习根据“今”预测“天”、根据“今天”预测“学”等。由于末批可能不足两条，实际每次更新的 token 数不完全相同；程序按实际张量统计，100 次更新共处理 11,160 个预测目标，包含重复读取。

**训练曲线**：更新后的模型，在全部训练序列上重新计算的平均 loss。

**验证曲线**：同一个时刻的模型，在不参与参数更新的验证文档上计算的平均 loss。验证阶段不反向传播，只检查它对另一篇文档预测得怎么样。

这里的 PPL 为 exp(loss)，可理解为预测的不确定程度，越低通常越好。但字符级词表、未知字符比例和验证文本都会影响数值，不能拿本次 PPL 与官方 Qwen 的 PPL 直接比较。

## 4. 真实文本训练的观察

| 更新次数 | 训练集 loss | 验证集 loss |
| --- | --- | --- |
| 0 | 4.8174 | 4.7474 |
| 10 | 3.7326 | 4.3377 |
| 20 | 2.8181 | 3.9918 |
| 30 | 2.0437 | 3.9366 |
| 50 | 0.8658 | 4.1727 |
| 100 | 0.0619 | 5.0140 |

前 30 步，两条曲线都下降：模型学到了一些能帮助预测另一篇文档的规律。之后训练 loss 继续下降，验证 loss 回升，说明模型越来越适应训练样本，对新文档的预测反而变差，这就是过拟合。

在每 10 步采样一次的记录中，第 30 步验证 loss 最低。程序保存的是最终第 100 步模型，并未实现自动保存最佳验证模型，因此“最终 checkpoint”不等于“本次验证最好的 checkpoint”。

本次训练约 1.38 秒，包含训练期间的周期评估，不含 Python 启动、数据准备、初始评估和后面的模型保存恢复。整个验证流程中 PyTorch 记录的峰值张量分配约 18.8 MiB，包含恢复模型和生成检查；显卡驱动、CUDA 上下文及框架缓存会另外占用显存，不能把这个数字当作整张显卡的总占用。

数据只有 3 篇短文，验证仅 1 篇；未登录字符会映射为未知 token，packing 会丢弃不足一个完整块的末尾。当前数字适合验证实现和观察现象，不能作为有代表性的语言能力评测。

## 5. 这次顺便修了什么

原先训练函数先完成全部训练、返回统计列表，外层才逐条打印并计算验证 loss。这会让不同步数的日志实际上用同一个最终模型评估。

现在每次参数更新后立即触发回调，到指定间隔就当场评估。验证函数还会在结束后恢复原来的训练/评估模式，避免训练途中验证改变后续 dropout 等行为。GPU 计时也增加同步，以便 step 时间包含计算完成。

修正后的原训练入口另外跑了 30 步：验证 loss 从第 1 步的 4.7171 下降到第 30 步的 4.2360。它使用默认 warmup/cosine、每次只累积 1 批，与上面的固定学习率、累积 2 批实验设置不同，数值应分别解读。

## 6. 自己复跑的小节点

在项目根目录运行：

```powershell
python -m unittest discover -s tests -v
python main_local_smoke.py --steps 100 --device cuda --output artifacts/my_local_run
```

`main_local_smoke.py` 会完成数据准备、初始评估、100 步训练、周期评估、参数保存恢复对比和 24 个 token 的生成形状检查。如果关键断言失败，会直接报错。

输出目录中的 `results.json` 保存配置、逐步统计和生成样例；`checkpoint.pt` 保存模型与优化器；`tokenizer.json` 保存字符词表。当前没有逐位一致的断点续训承诺，也没有验证官方权重兼容性。可使用 `--device cpu` 单独验证 CPU 链路，但本次主训练结果来自 CUDA。
