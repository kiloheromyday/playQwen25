# 阶段 1：模型结构与验证

这一阶段完成的是一个可以解释、可以运行、可以测试的 Qwen2.5 风格小模型。它的价值是建立正确的张量流和训练闭环，尚未涉及官方 tokenizer、官方数据集或大规模预训练。

## 1. 为什么先做 tiny 模型

Qwen2.5 官方模型至少是数亿参数级别。第一次写 decoder 时，如果直接启动大模型，遇到 shape、mask、dtype 或 label shift 错误，往往需要很久才能定位。tiny 模型只保留相同的结构，训练速度快，能够在 CPU 或单卡上验证。

这里的 `configs/tiny.json` 使用 2 层、64 hidden size、4 个 query heads、2 个 KV heads。它的规模很小，但仍然保留 GQA 和 SwiGLU 这两个关键结构。

## 2. 配置先于代码

`QwenConfig` 把模型形状集中管理。`hidden_size / num_attention_heads` 得到每个 head 的维度；`num_attention_heads / num_key_value_heads` 得到每个 K/V head 服务多少个 query head。

运行：

```powershell
python main_config.py
```

你需要看到 tiny 配置和 Qwen2.5 0.5B 参考配置的字段。参考配置只用于检查形状和理解规模，不代表在本机直接训练它。

## 3. Tokenizer 先用教学替代品

真正的 Qwen2.5 使用官方 tokenizer。当前项目先提供字符级 tokenizer，目的是让你能看到完整的 `文字 -> id -> 文字` 过程，并且不依赖网络下载模型文件。

它不适合拿来做最终能力实验，因为字符级切分会改变 token 数、词表规模和训练效率。后续接入真实 Qwen tokenizer 时，要同时更新 `vocab_size`，并保存 tokenizer 版本。

运行：

```powershell
python main_tokenizer.py
```

重点观察：同一段文字 encode 后得到 id，decode 后能够还原；中文、英文、代码的长度不同。

## 4. RMSNorm、RoPE、GQA、SwiGLU 各自负责什么

`RMSNorm` 控制 hidden vector 的数值尺度，使深层网络更容易稳定训练。它不改变张量形状。

`RoPE` 把位置信息作用到 Q/K 上，让 attention 能区分 token 的顺序。它也不改变张量形状，当前实现按 head dimension 的两半做旋转。

`GQA` 让 query heads 多于 K/V heads。它减少 K/V 的缓存和内存开销，当前实现通过 `repeat_interleave` 把 K/V 扩展到 query head 数量。

`SwiGLU` 是 token 内部的非线性 MLP。它使用 gate 和 up 两条投影路径逐元素相乘，再通过 down 投影回 hidden size。

运行：

```powershell
python main_components.py
```

这个入口只检查组件的输入输出 shape、数值是否有限，以及 GQA 的头数关系。它不证明模型已经学会语言，只证明这些局部计算能够跑通。

## 5. next-token loss 怎样出现

`QwenForCausalLM` 接收 `[batch, seq_len]` 的 token ids，经过 embedding、decoder layers、final RMSNorm 和 LM head，输出：

```text
logits: [batch, seq_len, vocab_size]
```

训练时使用 shift：位置 0 的输出预测位置 1 的 label，位置 1 的输出预测位置 2 的 label。代码中的 `labels= input_ids` 是一种常见接口写法，真正计算交叉熵时在模型内部完成错位。

运行：

```powershell
python main_forward.py
```

你应该看到 logits 的形状和一个标量 loss。loss 是一个数，因为它已经把 batch 和有效位置上的 token loss 做了平均。

## 6. 为什么单 batch 过拟合是第一道训练验收

如果模型连一小段固定 token 都不能反复记住，通常说明实现有 bug：label 没错位、causal mask 错了、梯度没有更新、学习率不合适、loss 计算错误或参数出现 NaN。

运行：

```powershell
python main_overfit.py
```

这个实验的期待是 final loss 明显低于 initial loss。它不是能力评测，也不能说明模型能泛化；它只验证 forward、backward 和 optimizer 更新形成了闭环。

## 7. 当前实现的明确边界

当前版本已经有：

- Qwen2.5 风格的核心 decoder 结构。
- GQA、RoPE、RMSNorm、SwiGLU。
- next-token loss。
- 教学 tokenizer、packing 和 checkpoint。
- 独立模块 smoke test。

后续还需要：

- 接入官方 Qwen tokenizer 并核对真实 config。
- 使用许可清楚的数据集建立稳定的 train/valid pipeline。
- 加入 BF16 autocast、梯度累积的真实训练循环。
- 加入 DDP，再根据显存选择 FSDP/ZeRO 或 Megatron。
- 增加 KV cache 的高效生成，而不是当前的重复前向生成。
- 加入 validation loss、PPL、tokens/s、显存和多卡扩展效率记录。

## 8. 本阶段向师兄汇报的说法

我先完成了 Qwen2.5 风格 decoder 的最小可运行实现。代码按配置构造模型，包含 RMSNorm、RoPE、GQA、SwiGLU 和 causal LM loss。每个组件都有独立 smoke test，整个模型可以完成 forward/backward，并能在固定 batch 上过拟合。当前 tokenizer 是教学版，下一阶段会接入官方 tokenizer和真实数据，再进入 BF16、多卡训练和评测。

## 9. 第二阶段新增的训练系统入口

`main_bf16.py` 检查当前设备是否支持 BF16 autocast，并验证模型在混合精度环境下能够完成 forward。

`main_metrics.py` 计算 validation loss 和 PPL。PPL 使用有效 token 的平均 loss 再取指数，不能把它当成准确率。

`main_checkpoint.py` 保存并恢复模型与 AdamW 状态，验证恢复前后 logits 完全一致。

`main_ddp.py` 使用 DDP 完成一个 forward/backward smoke test。直接运行时使用单进程 Gloo 作为本地检查；服务器上用 `torchrun --standalone --nproc-per-node=GPU数量 main_ddp.py` 才会启动真正的多进程多卡通信。
