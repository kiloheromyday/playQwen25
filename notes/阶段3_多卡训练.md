# 阶段 3：DDP 多卡训练入口

## 1. DDP 在做什么

DDP 是 DistributedDataParallel。它把同一个模型复制到多张 GPU，每张 GPU 处理不同的数据 batch。每次反向传播后，DDP 自动对各 rank 的梯度做通信归约，使每张卡的参数更新保持一致。

可以把一次训练理解成：

```text
全局 batch = 每张 GPU 的 batch size × GPU 数量 × 梯度累积步数
```

因此命令行里的 `--batch-size` 是“每张卡”的 batch size，不是全局 batch size。

## 2. 为什么需要 DistributedSampler

如果每个 rank 都读取完整数据集，那么每张卡会重复计算相同样本，速度没有真正提高。`DistributedSampler` 根据 rank 把数据索引切开，使不同进程看到不同的样本子集。

每个 epoch 或重新遍历 DataLoader 前要调用 `sampler.set_epoch(epoch)`，这样各 epoch 的 shuffle 才会变化。当前 smoke 入口在数据迭代器耗尽后设置新的 epoch。

## 3. 这个入口验证了什么

运行：

```powershell
python main_ddp.py
```

本机直接运行只做单进程的 DDP-compatible forward/backward 和 optimizer 检查，因为当前 Windows 环境没有可用的 NCCL 多卡通信。

在 Linux 多卡服务器上运行：

```bash
torchrun --standalone --nproc-per-node=GPU数量 main_ddp.py --steps 10
```

真正的 torchrun 路径会验证：

- 进程组初始化；
- NCCL 或 Gloo backend；
- 每个 rank 的 DistributedSampler；
- DDP 梯度同步；
- optimizer 更新；
- rank 0 汇总平均 loss 和 global tokens/s；
- rank 0 保存 checkpoint。

## 4. DDP 和 FSDP/ZeRO 的关系

DDP 的特点是每张卡都保存一份完整模型和 optimizer 状态，所以实现简单，但显存开销大。模型变大后，常见的下一步是：

```text
DDP -> FSDP / ZeRO -> Megatron TP + PP
```

FSDP 或 ZeRO 会把参数、梯度或 optimizer state 分片到多张卡；Megatron 的 tensor parallelism 和 pipeline parallelism 还会把层内矩阵或层堆栈拆开。当前项目先把 DDP 训练闭环跑通，再根据服务器 GPU 显存决定是否需要分片。

## 5. 向师兄汇报的说法

我已经把多卡入口从单纯的 forward/backward 改成了真实 DDP training smoke：每个 rank 使用 DistributedSampler 读取不同数据，完成 optimizer 更新，再通过 all-reduce 汇总 loss 和 global tokens/s，rank 0 保存 checkpoint。本机只能验证单进程路径，Linux 多卡服务器需要用 torchrun 验证 NCCL、同步效率和扩展比例。
